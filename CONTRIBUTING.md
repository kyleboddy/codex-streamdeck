# Contributing to Codex Command Center

Thanks for helping make tactile Codex workflows safer and more useful. This project sits between evolving desktop software and physical hardware, so reproducible evidence matters as much as code.

## Before opening an issue

1. Update Codex and Stream Deck only if you are prepared to record both versions.
2. Rerun `npm run install:local` after a Codex desktop update.
3. Run `npm run diagnose`.
4. Remove private workspace paths, task content, account information, device UUIDs, and serial numbers from any output you share.
5. Search existing issues for the exact Codex app/CLI and Stream Deck versions.

Use the provided bug or feature form when possible.

## Development setup

Prerequisites:

- Windows 10 or 11
- Node.js 24 or newer
- .NET SDK 10
- Codex Windows app
- Stream Deck software 7.5
- Stream Deck + for physical integration testing

Install locked dependencies:

```powershell
npm ci --ignore-scripts
npm --prefix com.driveline.codex-command-center.sdPlugin ci --omit=dev --ignore-scripts
```

Run the portable checks:

```powershell
npm test
npm run validate
npm run pack
```

Changes to the launcher, transport, controller, profile, or installer also require a local integration pass:

```powershell
npm run install:local
npm run diagnose
```

## Pull-request expectations

- Keep each change focused and explain the user-visible behavior.
- Add or update tests for protocol mapping, target selection, feedback, layout, and failure behavior.
- Record the Codex desktop, Codex CLI, Stream Deck software, and hardware model used for integration testing.
- Treat app archive findings as version-specific observations, not public API guarantees.
- Prefer schemas generated by the installed Codex CLI over hand-authored request shapes.
- Preserve loopback-only networking and fail-closed approval handling.
- Do not add keyboard/mouse automation as a silent fallback.
- Do not commit `dist/`, build output, installed plugins, logs, recovery bundles, device profiles containing UUIDs, or local runtime copies of Codex.

The pull-request template contains the minimum verification checklist.

## Protocol changes

When adding or changing an RPC method:

1. Generate current app-server schemas from the installed CLI.
2. Link the schema or official source that supports the request and response shape.
3. Add a unit or isolated probe that covers success and rejection behavior.
4. Verify whether the operation is safe from a peer client or must remain on the desktop bridge.
5. Confirm that ephemeral/system tasks cannot become hardware targets.
6. Document compatibility assumptions in `docs/reverse-engineering.md`.

Approval methods require an explicit result-shape test. Unknown approval shapes must continue to fail closed.

## Artwork and profiles

Keep action artwork distinct at action-list and hardware sizes. Any generated source artwork should include its provenance and prompt summary under `docs/assets/` or the corresponding source-art directory. Do not include third-party logos or imitate first-party device branding.

Profile edits must preserve the default physical contract:

- six working action keys;
- two intentionally blank keys;
- Brainpower on dial 1;
- Model on dial 2; and
- dials 3–4 left available.

## Commit style

Use short imperative subjects, optionally with a conventional prefix:

```text
feat: add active-task feedback
fix: reject unsupported approval shapes
docs: record app-server compatibility probe
test: cover multi-tick Ultra selection
```
